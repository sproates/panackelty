# Readable Panackelty: compiler batch

This batch applies the [authoritative standard](../CONTRIBUTING.md#readable-panackelty)
to every tracked `.panack` file in `src/compiler/`, under
[GI#304: Paired readability and testing](https://github.com/sproates/panackelty/issues/304).
It is the first compiler-wide readability pass, not acceptance of the entire
source-improvement programme. Public names, accepted syntax, diagnostics, exact
numeric behaviour and the bytecode version remain unchanged.

## What is easier to read

Each file now introduces its responsibility and important boundary. Declarations
and logical phases have breathing room; long signatures and calls break at
argument boundaries. Match arms have separate lines, and multi-step bodies no
longer hide several operations in one line. Existing algorithm and safety comments
are retained. No generated bytecode is hand-formatted.

The structural changes are deliberately bounded:

- String scanning expresses escaped-character consumption directly, without a
  three-level decision ladder or empty final branch.
- Literal escape decoding has a named responsibility and preserves the fallback
  for unknown escapes.
- Diagnostic UTF-8 rendering names the leading-byte modulus rather than embedding
  a nested conditional in an arithmetic expression.
- Conditional parsing separates arm construction from parsing the condition and
  then block, preserving explicit-else status and original written ranges.
- Namespace type compatibility separates guarded declarations, callable effects
  and recursive argument decisions. Known contradictions still dominate deferred
  evidence; holes never make `Void` a value.

For example, string scanning previously required following this ladder:

```panack
if escaped {
  escaped = false
} else {
  if source[cursor] == "\\" {
    escaped = true
  } else {
    if source[cursor] == "\"" {
      terminated = true
    } else {
    }
  }
}
```

The same state transition is now visible directly:

```panack
if escaped {
  escaped = false
} else {
  escaped = source[cursor] == "\\"
  terminated = source[cursor] == "\""
}
```

This pass does not prescribe an arbitrary nesting limit or replace substantive
algorithms with many tiny wrappers. Some parser/checker routines still have deep
error-dependent paths. Further decomposition should follow cohesive responsibilities
and measured costs; `else if` remains a separate language feature.

Legacy terminal expression semicolons are retained where they deliberately discard
a block value. Explicit separators after a field named `type` also remain: the
current lexer treats that spelling as a line-prefix keyword, even after a dot.
Removing those markers would change parsing rather than merely improve layout.

The batch adds 23 focused assertions: four scanner boundaries, six literal/Unicode
cases and thirteen namespace compatibility decisions. The latter include numeric
widening, forbidden narrowing, guarded deferral, effect coercions, exact callable
slots, generic arity, recursion and contradiction precedence in either slot order.
Existing source/bytecode, positioned diagnostic and bootstrap expectations are
preserved rather than replaced with successful-execution assertions.

## Validation and measurement

The layout-only stage reproduced the original compiler seed byte for byte.
Structural changes require a newly regenerated seed and digest, with compiler and
standard-library fixed-point validation. The final source must pass `make check`,
documentation checks, source coverage reader/policy/parity tests and fresh full
source collection before this batch can be integrated.

Source coverage counts expression/statement start lines. Expanding packed arms
changes that denominator even when the layout-only compiler bytes are identical.
Any coverage-policy update must explicitly report old/new counts, preserve the
manifest and protected items, and explain changed source structure. Formatting
does not by itself demonstrate new behavioural coverage.

The broader programme's IQ-1 weights remain 5% inventory/targets, 90% paired
batches and 5% final audit. This batch does not allocate the 90% across the entire
repository or declare every compiler file fully accepted. Whole-tree inventory,
component acceptance targets, unexecuted outcomes and deeper algorithm review
remain programme work. Keep merge/acceptance evidence distinct from a prepared PR.
