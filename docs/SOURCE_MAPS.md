# Validated source maps

Source maps connect an emitted function and instruction index to the expression
that produced it. A wrong location is worse than an unavailable location, so the
first public consumer reproduces the compilation locally before reporting a
source range. This is the U2 foundation for programme #180; checker explanations,
compilation reasons, runtime derivations and automatic trap locations remain
separate work.

## Commands

```sh
panack compile program.panack -o program.bc --source-map program.pmap
panack locate program.bc --source program.panack --source-map program.pmap --function main --instruction 0
```

Both compile destinations must be distinct, nonexistent files in directories the
caller controls. Normal compilation, execution and bytecode v9 are unchanged.
Mapping is opt-in; running a program never discovers or opens a neighbouring map.
`locate` compiles and checks sources but does not execute the user's program.
Function names and zero-based instruction indices come from `panack disasm`.
Generic calls identify their shared erased body, without claiming specialised
runtime type arguments.

A successful lookup prints `source-map: expression` or `source-map: lowered`,
followed by function, instruction, portable file identifier, half-open range,
one-based start/end line and column, and the captured expression. Offsets and
columns count Unicode code points, not UTF-8 bytes. Console output uses the
compiler's diagnostic escaping for control and non-ASCII characters. `lowered`
means generated machinery attributed to its enclosing expression. Missing
instruction entries, including statement stores, loop mechanics and implicit
returns, print only `source-map: unavailable`.

Missing, malformed, stale, oversized or incompatible map/artifact/source input
also produces `source-map: unavailable`, with exit status 0. The result means no
validated attribution is available; it does not prove the supplied bytecode is
valid or executable. Invalid command syntax exits 1. Creation failures exit 1
with a diagnostic and may leave a partial output pair, which the caller should
discard. Publication is not atomic. Existing file, hard-link and symlink outputs
are rejected; the second destination is checked again after the first write to
catch directory and case aliases. This is not protection against an adversary
replacing paths concurrently in the caller's output directories.

## Trust and identity

The installed compiler loads the explicitly supplied entry source, including
all transitive imports and the implicit standard-library core. It retains exact
source bytes, checks the program, and regenerates both bytecode and a canonical
map. Both supplied files must match the regenerated bytes exactly. Attribution
then comes from the newly compiled in-memory mapping. A coherently forged range,
source name, instruction or source snapshot cannot establish trust by changing a
checksum: the lookup must reproduce the complete pair.

This establishes agreement with the local compiler and explicit local sources.
It does **not** authenticate an original producer, certify source safety, or
verify a historical build without its sources/toolchain. The compiler and
explicit source tree are trusted inputs. A changed compiler may make an older
map unavailable even if its executable bytes still happen to match. Source
changes, including comments, unused imported modules and unused core text,
invalidate the pair. Unloaded neighbouring files are irrelevant.

Project identifiers are relative to the entry source's directory with a
`project/` prefix; standard-library identifiers use `stdlib/`. Relative imports
outside the entry directory may produce `project/../...` identifiers. These are
descriptive names, never paths read from a supplied map. Relocating unchanged
source and standard-library trees preserves the map. Explicit source symlinks
are allowed because the captured target bytes are reproduced, not trusted by
pathname alone.

The compiler rereads the loaded sources before accepting the result, rejecting
observed changes since loading. This is not an atomic filesystem snapshot or a
promise that the editor's current contents have not changed immediately after
validation. Locations describe the exact captured bytes embedded in the map.
Use a stable source checkout for reproducible investigations.

## Format and bounds

The canonical format starts with `PANACKMAP1\nlocal-replay-v9\n`, followed by:

1. Entry identifier, then the complete executable artifact.
2. Snapshot count, then snapshots sorted by portable identifier; each has its
   identifier and complete UTF-8 source text.
3. Function count, then functions in emitted order, each with its name and entry
   count. Entries are ordered by instruction index and contain instruction index,
   snapshot index, start offset/line/column, end offset/line/column, and a lowered
   flag (0 or 1).

Counts and coordinates use big-endian unsigned 32-bit integers; text and byte
blobs have a 32-bit UTF-8/byte length prefix. The lowered flag is one byte.
Snapshot indices are zero-based. The decoder is intentionally absent from the
production consumer: it reads foreign files only up to the expected locally
computed sizes and compares exact bytes. Foreign lengths, paths and indices
never control allocation, file access or attribution. Format changes require a
new marker and explicit compatibility tests; v9 executable bytes stay separate.

Map compilation limits each source to 1 MiB of valid UTF-8, the complete loaded
closure to 8 MiB and 256 files, and the resulting sidecar to 16 MiB. These are
input/output limits, not a hard CPU or memory budget for compiling arbitrary
trusted source. Serialisation joins chunks in a balanced tree to avoid copying
the captured source closure for every instruction. Lookup performs compilation
again and therefore has compilation-scale cost; see the measured compiler and
small-fixture results in [the validation profile](../tests/VALIDATION_PROFILE.md).

**Sidecars contain the full source closure and artifact, including comments and
unused imported code.** Review their contents before sharing them. Portable
identifiers remove checkout-root names from metadata, but source literals and
artifact constants can still contain absolute paths or sensitive material.
There is no source-redaction or signature mode in this delivery.

## Acceptance evidence

The self-hosted unit and CLI suites cover deterministic serialisation, bytecode
identity, direct/lowered/unavailable locations, Unicode/imported generic ranges,
argument and size bounds, changed dependencies, corrupt maps, missing pairs and
output collisions. The native observer suite checks independently specified
locations against actual VM traps and constructs coherent binary forgeries.
It also checks core changes and relocated trees. All existing span/emitter tests
remain in place. The earlier JSON/checksum experiment has been removed: its
finding that checksums do not authenticate attribution is addressed by local
reproduction, not by another self-asserted producer identity.
